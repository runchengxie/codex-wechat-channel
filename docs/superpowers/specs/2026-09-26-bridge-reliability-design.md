# 微信桥接访问控制与可靠性设计

本文记录此前可靠性改动的设计与实施计划。文件路径和检查方式以当时的 JavaScript 版本为准，当前构建与验收方式见 `docs/plan-and-progress.md`。

## 背景与目标

`codex-wechat-channel` 将微信消息送入 Codex，并为每个聊天保存独立 thread。当前实现没有微信发送者白名单，消息轮询游标会在消息处理前落盘，普通 turn 没有完成超时，app-server 断线后也不会恢复连接。这些行为可能让未授权用户触发 Codex 操作、让已拉取消息在进程退出时丢失，或让同一聊天的队列一直卡住。

本次改动在保留 JavaScript 和现有部署方式的前提下，补上可选的发送者白名单、批次游标提交、turn 超时、app-server 按需重连，以及覆盖这些行为的自动化测试和 CI 检查。

## 设计范围

### 微信发送者白名单

- 新增环境变量 `CODEX_WECHAT_ALLOWED_USERS`，接受逗号分隔的微信发送者 ID。
- 未设置或解析后为空时，保持当前行为并在启动日志中明确警告，提示配置白名单。
- 设置后，只有 `from_user_id` 在白名单中的消息才进入命令解析、Codex thread 或回复流程。
- 私聊和群聊使用同一发送者 ID 规则。允许的发送者可在其参与的群聊中触发桥接，未允许的发送者在私聊或群聊中都会被忽略。
- 不记录被忽略消息的正文或 context token。文档说明此策略是可选限制，空配置仍会放行。

### 轮询游标与消息处理

- 每次收到一批消息后，等待该批所有消息任务结束，再保存响应中的 `get_updates_buf`。
- 一批消息中的任务继续通过现有会话队列串行处理。同一轮询批次全部结束前不发起下一次轮询，避免积累无限多批待处理消息。
- 只有该批任务全部完成或被明确忽略时才提交新游标。Codex 处理失败后，如果失败提示成功发给用户，这条消息视为已完成。若失败提示也发送失败，任务会继续报错，保留旧游标并进入现有重试退避流程。
- 该策略提供至少一次处理语义。进程在外部回复已发送、游标尚未保存时退出，重放可能导致重复回复。本次不引入消息 ID 去重存储，因为当前代码没有确认稳定的微信消息 ID 字段。

### turn 超时

- 普通 `turn/start` 完成等待使用 180 秒超时，与现有代码审查等待时限一致。
- 超时后拒绝对应 Promise，并从活动 waiter 表中删除，释放该聊天的后续消息。
- 迟到的 app-server 通知不得再次完成已超时 waiter，也不得无限增加缓存。

### app-server 重连

- WebSocket 关闭时将连接标记为不可用，拒绝未完成请求，并清除当前连接对应的已加载 thread 缓存。
- 后续消息处理开始前检查连接状态。断开时重新连接并完成 `initialize`。
- 并发消息共享同一个连接尝试，避免同时启动多个内置 app-server 或重复初始化同一个 WebSocket。
- 初始化完成前连接不视为可用。连接失败会清理半成品连接，后续消息可以重新连接。
- 连接失败沿用消息错误处理和轮询退避，不在单条消息内无限重试。未成功回复的消息可随未提交游标再次处理。
- WebSocket 断开但内嵌 app-server 子进程仍运行时，重连复用该进程。子进程退出处理会核对进程身份，避免旧进程影响新连接。

### 测试与 CI

- 用 Node.js 内置测试运行器验证白名单解析及私聊、群聊的允许和拒绝路径。
- 验证轮询批次全部结束后才提交游标，失败时游标不前移，并验证批次处理提供的背压行为。
- 验证 turn 超时会拒绝调用并清理 waiter。
- 验证 WebSocket 断开后 thread 缓存失效、并发重连只建立一个连接。
- GitHub Actions 在 Node.js 22 上运行 `npm run check`、`npm test`，并使用 Bash 检查 watcher 脚本语法。
- 不在本次增加 ESLint、第三方运行依赖或 TypeScript 编译链。

## 不在本次范围

- 将 `.mjs` 迁移为 TypeScript。作为后续独立改动评估，避免同时改变运行时行为和整个构建、发布方式。
- 清理历史图片文件。当前 thread 历史可能引用本地图片路径，自动删除需要另行确定保留期限与引用失效规则。
- 大规模拆分 `CodexAppServerClient` 或 `servicectl.mjs`。本次只为新增可测行为提取最小必要的边界。
- 引入消息去重数据库、群聊白名单或按会话配置不同权限。

## 兼容与运维影响

- 未配置白名单的现有部署继续按当前方式工作，但启动时会收到访问控制警告。
- 设置白名单后，非允许发送者不再触发 Codex，也不会收到桥接回复。
- 若一批消息处理失败，轮询游标保持不变，服务可能重放同一批消息。调用方应接受至少一次语义可能产生的重复回复。
- npm 运行时仍要求 Node.js 22 或更新版本，不增加运行时依赖。

## 验收标准

1. 空白名单配置保留兼容行为，并在启动时输出明确警告。
2. 配置白名单后，只有白名单发送者的消息进入桥接流程。
3. 批次未处理完成时，持久化游标不前移。批次成功后再落盘。
4. turn 超时会释放该聊天队列。
5. app-server 断线后，后续消息能触发单次连接恢复，并重新恢复 thread。
6. 新增测试在本地和 CI 中通过，watcher 脚本语法检查纳入 CI。
