# 代码维护检查

## 复现方法

在仓库根目录执行：

```sh
npm ci
npm run check
npm run audit:code
node dist/tools/maintenance-report.js --json > /tmp/codex-wechat-maintenance.json
npm ls --all
npm audit --audit-level=high
git submodule status
```

报告扫描 `cli.ts`、`src/`、`scripts/`、`test/` 和 `tools/` 中的 TypeScript 与 `.mjs` 文件。生成目录、依赖目录、Markdown 和 Bash 文件不计入代码指标。JSON 包含每个文件和函数的指标，以及依赖边和调用边，适合比较两次修改。扫描顺序固定，报告不附带时间戳。

2026 年 9 月 26 日的本地环境为 Node.js 24.21.0、npm 11.19.0、TypeScript 6.0.3。项目运行要求为 Node.js 22 及以上，类型定义使用 `@types/node` 22.20.4。PDF 和 DOCX 文本提取依赖 `pdfjs-dist`、`mammoth`，依赖版本由 `package-lock.json` 固定。仓库当前没有 submodule。

开发工具加入后发现旧版 SonarJS 的间接依赖存在高危告警，升级 ESLint 和 SonarJS 后，在线审计返回零漏洞。网络故障时应让审计失败，离线安装提示不能替代在线核查。后续以当前锁文件的 `npm audit` 结果为准。

## 指标含义

| 指标 | 计算方法与限制 |
| --- | --- |
| LOC | 物理行数，含注释和空行，不把结尾换行另计一行。函数行数从语法节点起始位置算到结束位置 |
| 圈复杂度 | 每个函数从 1 开始，`if`、循环、`catch`、三元表达式、非默认 `case` 及 `&&`、`\|\|`、`??` 各加 1。嵌套函数单独计数 |
| 认知复杂度近似值 | 分支和循环按 1 加当前嵌套深度计数，`switch` 同样处理。逻辑运算和 `else` 各加 1。这是项目自定近似算法，不能与 Sonar 的分数直接比较 |
| 依赖图 | 从静态 `import` 和 `export ... from` 建图，包含类型依赖。`typeOnly` 标记整条语句是否为纯类型导入。动态加载不计入 |
| 入度和出度 | 引用该模块的本地模块数，以及该模块引用的本地模块数，同一模块重复导入只计一次 |
| 循环依赖 | 报告依赖图的强连通分量，包含模块自引用。每组结果表示相互可达的模块集合 |
| 调用图 | 使用 TypeScript 类型检查器解析调用签名，记录能定位到本次扫描中函数实现的调用点。外部调用和无法解析的调用另计数量 |

调用图描述静态解析结果。回调、动态派发、运行时替换方法等行为可能与解析结果不同，不能据此认定某个函数是死代码。删除代码前还要检查 CLI 入口、导出接口、测试、反射和部署脚本。

`test/maintenance-report.test.ts` 用小型源码样例检查行数、嵌套函数、分支、类型导入、循环依赖和跨文件调用，避免仅凭报告输出看起来合理就采信指标。

## 重构后的检查

命令分发改为独立处理函数，app-server 分离回合结束处理，启动配置与轮询分开，消息内容提取也拆出了独立步骤。权限切换功能加入前扫描 35 个文件、4190 行，最高圈复杂度为 18，模块循环依赖仍为 0。运行 `audit:code` 可取得后续修改后的值，首轮表格保留用于对照。

ESLint 对全部 TypeScript 源码、测试和审计工具启用未使用变量、显式 `any`、Promise 处理和类型忽略检查。圈复杂度上限为 20，嵌套深度上限为 4，SonarJS 认知复杂度上限为 20，没有针对现有文件关闭这些规则。报告中的自定义认知复杂度近似值与 SonarJS 计分方式不同。

c8 从编译输出采集覆盖率并映射回源码。`--all` 将未加载的生产文件计入统计，额外检查确保报告包含全部生产文件（目前为 17 个）。门槛为行 70%、分支 60%、函数 60%。测试和开发工具不计入生产覆盖率，CLI 与服务脚本没有被排除。一次配置检查曾发现源映射后的过滤会生成空报告，现已用专门测试防止该情况通过门禁。

补测还发现 `probe` 成功后保留超时计时器的问题，现已在操作结束时清理。当前测试对微信、Codex 和 systemd 使用替身，真实账号登录、跨进程异常恢复和实际服务部署仍需真实环境验收。

## 数据和构建产物的去向

微信轮询返回消息和游标。消息按会话排队，进入命令处理或 Codex 对话。回复发送完成后，该批次才保存游标。错误通知发送失败时，批次失败并保留旧游标，下次轮询可能再次取得这些消息。当前没有持久化的逐消息去重记录。

账号信息、上下文令牌、线程记录和游标写在用户目录的 `~/.codex/channels/wechat/`。图片经过下载和解密，保存在该目录的 `media/` 下，再以本地图片输入传给 Codex。txt、md、csv、json、pdf、docx 附件下载并解密后只把限长文本传给 Codex。PDF 最多提取前 100 页，不做 OCR。DOCX 使用 Mammoth 提取纯文本。视频下载到 `media/` 临时目录，用系统中的 `ffprobe` 检查时长，再由 `ffmpeg` 抽取最多 6 帧和受限 MP3 音轨，分别作为本地图片和音频输入传给 Codex，回合处理完成后清理临时文件。消息类型保留 `group_id` 字段的解析，但当前微信 iOS ClawBot 接入方式只支持私聊，群聊尚未作为受支持功能。日志会包含部分消息和回复文本，不能当作不含用户内容的普通构建日志发布。

源码经过 `tsc` 生成 `dist/` 中的 ESM JavaScript。构建脚本另将 Bash 监视脚本复制到发布路径，`package.json` 的 `files` 字段决定 npm 包内容，`bin` 指向 `dist/cli.js`。使用者运行已编译的 JavaScript，开发和 CI 使用 TypeScript、类型定义及后续质量检查工具。`dist/` 和覆盖率输出不提交到 Git。

这些数据与产物流向来自入口、持久化函数和构建脚本的人工核对。AST 报告不能自动证明文件内容的完整来源，也不能证明真实微信、Codex 登录和 systemd 部署均正常。CI 使用本地替身检查边界行为，真实环境验收需要单独执行。
